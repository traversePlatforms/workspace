## It was verified, not eyeballed

A QR code that does not scan looks exactly like one that does. Every PNG the generator writes is decoded back with jsQR and the decoded string compared character-for-character with the source URL, at **1200 px, 400 px, 240 px and 160 px** — the small sizes produced by nearest-neighbour downscaling, which is harsher than a phone camera. The build prints PASS or FAIL per variant and says outright not to ship a failure.

Current result: **all four pass at every size.** 33 modules, 41 including the quiet zone, error correction level H.

If you edit the artwork, re-run it. That check is the whole point of the script.

```
npm i qrcode jsqr pngjs        # somewhere OUTSIDE OneDrive
QR_DEPS=<that>/node_modules node build-qr.mjs
```

Dependencies deliberately live outside this folder — a `node_modules` tree here would be synced file-by-file by OneDrive.

## Three decisions worth knowing

**Generated locally, not through an online QR service.** Free QR generators frequently hand back a code that points at *their* domain and redirects to yours, which means the code dies if they change their terms, start charging, or shut down — and it lets them count and profile every scan. These encode the destination directly. Nothing about the link was sent anywhere.

**The accent appears nowhere in the scannable geometry.** The data modules and all three finder patterns are Pine Black on Bone, about 14:1. The accent colour is used only for the centre mark, which sits in a cleared reserve and carries no data — which is why recolouring it cannot affect decoding, though the build re-verifies regardless.

**The centre mark is Turf `#2F7A4F`, not Sage.** Palette A, 2026-09-25. It sits on Bone, and Sage is 1.64 on Bone — it would disappear. Turf is 4.25, a mark-and-rule value, which is exactly what this is. Same rule the social kit follows for its light-ground avatar. The old Ember mark was 2.7:1 on Bone and decoded fine, but on a lenient software decoder in perfect light, not a phone in a driveway at dusk.

**The code is never inverted.** The obvious move for a dark-first brand is light modules on a dark ground, and it is the standard way to produce a QR that a meaningful share of phones refuse. Where the code has to sit on something dark, `sixfold-qr-on-dark-tile.png` puts it on a Bone plate instead.

**Rounded modules and ringed finders are cosmetic only.** The 7:5:3 finder geometry and the one-module ring width are preserved exactly, so the locator pattern a scanner searches for is intact. The centre reserve is cleared one module wider than the plate that covers it — without that, the plate lands on live modules and slices them into crescents.

## Printing it

The common rule of thumb is that a QR needs to be about **1/10th of the distance it will be scanned from** — read at arm's length, roughly 25–30 mm across is the sensible floor; on a yard sign read from the pavement, considerably bigger. Do not go below about 20 mm for a hand-held piece.

Two things that break a printed code more often than size: **losing the quiet zone** (the blank margin is part of the code — do not crop to the edge of the modules or set type inside it) and **printing it on a tint or a photograph**. Keep it on flat white or flat Bone.
